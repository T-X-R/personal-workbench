# ADR 0001：使用 Tauri 2 作为个人工作台桌面宿主

- 状态：提议
- 日期：2026-09-03

## 背景

工作台是单用户、本地优先的个人 App，不需要公开发布，但需要稳定的本地数据、文件访问、系统快捷键和可选的原生能力。未来的业务能力需要可插拔，不能把平台和业务页面绑死。

## 决策

使用 Tauri 2 承载 React + Vite + TypeScript 前端。平台通过受控的 Tauri 命令提供文件、SQLite 和系统能力；能力包只依赖 `CapabilityHost`，不直接访问 Tauri API。

## 选择理由

- Web 前端开发体验与桌面交付兼得。
- 相比 Electron，默认包体和运行时占用更小，且本地 App 不需要完整 Node 运行时。
- 原生能力集中在平台 Adapter，能力契约保持与宿主实现解耦。
- 若未来改用 Electron，仍可保留 `Capability Contract`，迁移面集中在宿主 Adapter。

## 代价与缓解

- 团队需要维护少量 Rust 代码：限制在平台 Adapter，并为命令写集成测试。
- 动态加载外部能力包需要额外的资源协议、版本校验和权限审核：第一版只支持本地导入并显式确认。
- Tauri 插件生态不如 Node 广：遇到必须依赖 Node 原生 SDK 的能力时，再评估 Electron Adapter，不提前为此增加复杂度。

## 不在本 ADR 中决定

- 远程能力市场、签名与自动更新。
- 具体模型供应商和 Agent 编排方式。
- 多工作区、云同步和跨设备账号。
